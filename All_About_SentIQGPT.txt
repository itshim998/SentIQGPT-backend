SENTIQGPT - FULL PROJECT HANDOFF AND CONTEXT

Purpose

SentIQGPT is a general-purpose AI assistant with:
- conversational chat
- streamed responses
- persistent memory
- file ingestion and contextual file analysis
- image generation with provider fallback
- web search for current/factual lookups
- local-first client storage via IndexedDB

It is a dual-runtime system:
- TypeScript/Node.js backend for orchestration, API, tool routing, and app logic
- Python FastAPI LLM gateway for provider routing, key rotation, and cache-backed model access

Operationally, the project is built around the idea that Gemini does the heavier reasoning/conversation work, while Groq is used for fast classification/planning/summarization tasks.


============================================================
1. CURRENT HIGH-LEVEL ARCHITECTURE
============================================================

Main layers:

1. Frontend
- Main UI currently lives in frontend/index.html as a single-file app with inline CSS and inline JS modules.
- Browser stores chats, memories, files, and config in IndexedDB.
- Frontend talks directly to backend HTTP endpoints.

2. Backend app server
- backend/server.ts
- Express + TypeScript
- Exposes health, chat, stream, memory, file upload, image generation, config, and audit endpoints.
- Applies validation, rate limiting, audit logging, image quota enforcement, and prompt injection checks.

3. Orchestration/intelligence layer
- backend/orchestrator/*
- Builds context, plans tool usage, executes tools, merges outputs, and optionally reflects on responses.

4. LLM gateway
- backend/llm_service.py and root llm_adapter.py
- FastAPI service on port 3002
- Routes tasks to Gemini or Groq
- Handles provider key rotation, token buckets, and shelve-based caching.


============================================================
2. PROJECT GOAL AND PRODUCT BEHAVIOR
============================================================

User-facing capabilities:
- Ask questions and get streamed AI responses
- Ask follow-up questions across chat history
- Store and reuse important user facts/preferences/projects as memories
- Upload files and use extracted text in chat context
- Generate images from prompts
- Generate chat titles automatically from the first exchange
- Use web search when a question requires current data or factual lookup

The intended behavior is:
- normal conceptual/general questions should be answerable from model knowledge
- factual/current/recent/product/medicine/entity questions should be web-searched first
- image requests should route to image generation
- explicit personal-memory requests should route to memory logic

5. REQUEST/RESPONSE CONTRACTS
============================================================

Chat request shape (server-side validation in backend/validation/schemas.ts):

POST /api/chat or /api/chat/stream
{
	"message": "string, 1..10000 chars",
	"conversation_id": "optional string",
	"context": {
		"recent_messages": [{ "role": "user|assistant", "content": "..." }],
		"memories": [{ "type": "...", "summary": "..." }],
		"file_references": [{ "filename": "...", "extractedText": "..." }]
	}
}

Non-stream chat response roughly returns:
{
	"route": "normal_chat | image_generation | file_analysis | memory_update",
	"reply": "optional string",
	"disclaimer": "optional string",
	"image": { ...optional image payload... },
	"memory": { stored, type?, summary?, importance? },
	"confidence": number
}

Stream endpoint emits SSE events like:
- token events: { type: "token", text: "..." }
- memory events: { type: "memory", memory: {...} }
- search events: { type: "search", search: { query, results[] } }
- error events: { type: "error", error: "..." }
- done marker: [DONE]

Image generation request shape:
{
	"prompt": "string, 1..2000 chars",
	"style": "optional string",
	"size": "256x256 | 512x512 | 1024x1024"
}

Image generation response shape from /api/images/generate:
{
	"type": "image",
	"url": "data URL or hosted URL",
	"prompt": "final prompt",
	"provider_used": "provider name",
	"success": true,
	"remaining": number,
	"limit": number,
	"image_url": "legacy compatibility field",
	"image_base64": "legacy compatibility field"
}

6. ORCHESTRATION AND TOOL SELECTION
============================================================

Main orchestrator:
- backend/orchestrator/aiOrchestrator.ts

Its job:
1. build context
2. run planner and memory pipeline in parallel
3. execute the plan
4. merge results
5. optionally run reflection/improvement
6. optionally cache final answer

Planner:
- backend/orchestrator/planner.ts
- uses Groq via route_classify task
- generates up to 3 ordered steps
- available tools:
	- conversation
	- image_generation
	- file_analysis
	- memory_update
	- web_search

Executor:
- backend/orchestrator/toolExecutor.ts
- sequentially executes plan steps
- threads prior step context into later steps

Legacy detector:
- backend/orchestrator/toolDetector.ts
- older route classifier still exists, but planning/execution path is the newer system

CURRENT IMPORTANT CHANGE:
- A new deterministic classifier was added in backend/orchestrator/queryClassifier.ts
- It classifies a query into:
	- general_knowledge
	- real_time_information
	- factual_lookup
	- personal_context
	- image_generation
- If classification says real_time_information or factual_lookup, web search is required before answering.

This classifier now acts as a safety net in two places:
- non-stream path: after planning, aiOrchestrator can override the planner and force a web_search step
- stream path: backend/server.ts now classifies first and injects web search results before building the chat prompt

This is important because before this fix, the stream endpoint bypassed the orchestrator and answered directly from model knowledge, which caused bad behavior for current/factual questions.

7. QUERY CLASSIFICATION AND WEB SEARCH LOGIC
============================================================

Current query classification file:
- backend/orchestrator/queryClassifier.ts

What it does:
- uses deterministic regex/pattern matching
- zero LLM cost
- near-instant routing hint

Queries that should trigger web search include:
- current events
- recent news
- sports scores/tournaments/results
- medicines/drugs/supplements
- products/releases/reviews/specifications/prices
- technical documentation / APIs / frameworks
- named entities that may not be in training data
- statistical facts that may have changed

Examples expected to trigger search now:
- "What is the current T20 cricket world cup?"
- "Who won the IPL yesterday?"
- "What is Tricium Joints medicine used for?"
- "Latest Nvidia GPU release"
- "What is Ozempic used for?"

The classifier also strips conversational filler for better search terms through buildSearchQuery(...).

10. MEMORY SYSTEM
============================================================

Memory processor:
- backend/ai/MemoryProcessor.ts

Pipeline:
1. classifyMemory(...)
2. summarizeMemory(...)
3. generate embedding for semantic retrieval

Memory types:
- identity
- preference
- project
- knowledge

Storage model:
- server does not persist long-term memory in a database
- memories are returned to the client and stored client-side in IndexedDB
- later requests send memory summaries back as part of context

Memory retrieval path:
- backend/context/contextBuilder.ts
- tries semantic search first via embedding cosine similarity
- falls back to keyword selection when embeddings unavailable

Conversation compression:
- backend/context/contextCompressor.ts
- keeps a 6-message recent window
- summarizes older conversation via Groq into 1-2 sentence summary

Memory significance:
- this app is effectively local-first for personal context
- browser storage matters a lot because memories/chats/files live client-side

11. FILE INGESTION AND FILE CONTEXT

Supported logical file types:

- txt/plain text
- images

Accepted MIME/extensions include:
- pdf

- css

- ts
- json
- xml
- md
- py
- java
- cpp
- c
- rs
- go
- png
- jpg
- jpeg

Key safeguards:
- 10 MB max file size
- path traversal prevention in filename validation
- unsupported MIME blocked

Extraction behavior:
- txt/code-like files: direct utf-8 text extraction
- pdf: tries pdf-parse, falls back to regex-like text extraction
- image: stores metadata-style placeholder rather than OCR text

File context building:
- backend/context/fileChunker.ts and contextBuilder.ts
- large file text is chunked and relevant chunks selected for a query

IMPORTANT CURRENT QUIRK:
- backend schemas expect file_references[].extractedText
- frontend request assembly in frontend/index.html currently sends extracted_text in some paths
- that naming mismatch is a real integration risk and should be treated as a known bug candidate

24. IMPORTANT KNOWN QUIRKS / RISKS / SHARP EDGES
============================================================

1. frontend SSE parser does not yet handle search events
- backend emits them
- frontend currently ignores them
- source display in UI is incomplete even though backend search context is used

2. possible file reference naming mismatch
- backend expects extractedText in file_references
- frontend sometimes builds extracted_text objects from local file store
- this is a verified integration risk and may affect file-context routing

3. architecture doc is partially stale
- docs/ARCHITECTURE.md is helpful, but current code has moved beyond it
- frontend especially is more single-file and more production-hardened than the doc suggests

4. active frontend source of truth is index.html
- there are split JS/CSS files in workspace, but current UI behavior is embedded inline in index.html

5. client-side storage is critical
- memories/chats/files are stored locally in the browser
- clearing browser storage materially changes app behavior/context

6. stream and non-stream paths are not identical
- /api/chat uses full orchestrator pipeline
- /api/chat/stream still builds a direct chat prompt after injecting search context and running background memory processing
- this means behavior parity is improved but still not fully unified

26. WHAT ANOTHER AI SHOULD ASSUME WHEN WORKING ON SENTIQGPT
============================================================

If you are ChatGPT or another AI joining this project, assume the following:

- The real backend intelligence is in backend/server.ts, backend/orchestrator/*, backend/ai/*, backend/tools/*, and llm_adapter.py.
- The real active frontend is frontend/index.html, even though legacy-style split frontend files also exist.
- The system is local-first on the client: chats, memories, and files live in IndexedDB and are echoed back to the backend as context.
- Web search is now a first-class capability and should be used for current/factual/entity/medicine/product questions.
- Do not remove the deterministic query-classifier safety net.
- Be careful with schema/property names between frontend and backend; some naming drift exists.
- Keep stream and non-stream behavior aligned when changing tool-selection logic.
- Avoid exposing raw internal/provider/debug details to the end user UI.
- When making architecture changes, verify both TypeScript build health and runtime contract compatibility with the inline frontend.

27. SHORT HANDOFF SUMMARY
============================================================

SentIQGPT is a dual-model AI assistant: Express/TypeScript handles app logic and orchestration, while a Python FastAPI LLM gateway routes tasks to Gemini (reasoning/chat) and Groq (planning/classification/memory summarization). The frontend is currently a single-file IndexedDB-based SPA in frontend/index.html. The system supports chat, memory, file analysis, image generation, and now deterministic web-search triggering for factual/current queries. The most important current realities are: active UI logic is inline in index.html, web search has recently been hardened through query classification, stream and non-stream paths are similar but not identical, and there are still a few integration quirks such as unhandled SSE search events in the frontend and a probable file-reference naming mismatch.
